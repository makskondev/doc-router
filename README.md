# DocRouter — сервис-«курьер» для документов

Один сервис (ASP.NET Core, 1 реплика в k8s), который «водит» файлы по шагам: подпись (REST) → проверка → архив подписей (PostgreSQL) → запись в Oracle → перемещение. **Состояние процесса не хранится**: «где документ» определяют папки и вью; при сбое шаги проходятся заново на следующем опросе. **PostgreSQL** хранит: независимый архив подписей и метаданных, журнал операций (все типы) и состояние документов **только для долгих потоков** (`.Stateful()`).

> Каркас написан без компиляции (в среде не было .NET SDK). Первый `dotnet build` может показать мелкие правки (версии пакетов, API SMBLibrary).

## Быстрый старт
```sh
./create-solution.sh && dotnet build && dotnet test
dotnet run --project src/DocRouter.Host
```
k8s: `replicas: 1`, `strategy: Recreate`; probes: `/health/live`, `/health/ready` (цикл опроса жив), `/health/deps` — только диагностика (SMB, Oracle, PostgreSQL).

## Типы документов (в коде: `src/DocRouter.Routes/DocumentDefinitions.cs`)
| Семейство | Тип | Источник | Цепочка шагов |
|---|---|---|---|
| 1. Брокерские отчёты | `BROK_REP` | вью `report_log_vw` | FindFile (папка по полям: pdf → signed_docs; EMAIL=1 → brok_rep\email; иначе brok_rep) → RestSign → Verify → ArchiveSignature → MarkSigned. Файл не перемещается |
| 2. Депозитарные отчёты | `DEPO_REP_DO`, `DEPO_REP_JRN` | папка depo_reports, маски `*_ДО.*`, `*_жрн.*` | FindFile → ExtractClientCode → RestSign → Verify → PlanTargetPath → ArchiveSignature → CreateFileRecord → MoveFile (signed_docs) |
| 3. Депозитарные документы | `DEPO_NOTICE`, `DEPO_APPLICATION` | папка was_signed\depo + `.sig` | FindFile → ReadSignatureFile → Verify → PlanTargetPath → ArchiveSignature → CreateFileRecord → MoveFile → DeleteFile(.sig) |
| 4. Брокерские документы | `BROK_NOTICE` | папка was_signed\brok + `.sig` | то же, что 3 |
| 5. Брокерские заявления (ручное подписание) | `BROK_APPLICATION` **(Stateful)** | вью `doc_to_sign_vw` (ID, имя файла, код клиента) | FindFile → SendToManualSigning (docs → to_sign\brok) → WaitForManualSignature (файл + .sig в was_signed\brok, до 24 ч) → ReadSignatureFile → Verify → PlanTargetPath (corp\signed_doc) → ArchiveSignature → MoveFile → DeleteFile(.sig) → **MarkSigned (Oracle, последним)** |

Для 3 и 4: документ без `.sig` дольше 24 часов → письмо «подпись не получена» (на каждом опросе, пока не появится).

Типы — первоклассные сущности: у каждого своя маска, «вид» (`.Kind("ДО")`, уходит в Oracle и архив), группа адресатов (`.NotifyTo(mail.Depo)`). Общая цепочка нескольких типов — обычная локальная функция (`DepoReport(...)`, `SignedDoc(...)`).

## Порядок действий (почему он такой)
1. **Подпись берётся из архива PostgreSQL, если документ уже подписывали** (тот же тип, источник и SHA-256 содержимого): повторный опрос после сбоя не подписывает заново, а архив и Oracle не расходятся.
2. **ArchiveSignature** (PostgreSQL) идёт сразу после проверки — собственная копия подписи появляется первой.
3. **PlanTargetPath → CreateFileRecord → MoveFile**: Oracle нужен путь сохранённого документа, поэтому он определяется ДО перемещения (детерминированно: при коллизии имени — суффикс даты-времени изменения исходного файла). Перемещение — последнее действие, и триггером служит сам файл, поэтому любой сбой лечится повтором.

## Долгий поток с состоянием: BROK_APPLICATION
Запись в `doc_to_sign_vw` остаётся во вью, пока документ ждёт человека, поэтому вью — единственный триггер, а «где документ и что уже сделано» хранится в PostgreSQL (`document_state`: состояние прохода в `jsonb` + список выполненных шагов). Правила:
- после каждого успешного шага состояние сохраняется; на следующем опросе выполненные шаги **пропускаются** (шаги всё равно идемпотентны на случай сбоя между действием и сохранением);
- срок ожидания подписи (24 ч) считается **от момента отправки на подпись**, а не от времени изменения файла; после срока — строка в сводке на каждом опросе;
- процедура Oracle («ID + подпись») вызывается **последним шагом**: запись исчезает из вью только когда файл подписан, проверен, заархивирован и перемещён в `\\fd\corp\signed_doc`, поэтому дыры «запись ушла, файл остался» нет;
- содержимое файла в состоянии не хранится; сбой PostgreSQL = ошибка в сводке, повтор на следующем опросе;
- запись, вернувшаяся во вью после завершения (или когда все шаги выполнены, а запись всё ещё видна), начинает обработку заново.

## Журнал операций (все типы)
Таблица `document_operations`: одна строка на документ — когда впервые замечен, на каком шаге остановился, число неудачных проходов, последнее сообщение, итог (`waiting` / `failed` / `completed`), итоговый путь, номер запуска. **Только наблюдаемость:** на ход обработки не влияет, сбой записи в журнал логируется и обработку не ломает. Вместе с `signed_documents` (подпись, файл, SHA-256, пути) отвечает на вопрос «что произошло с документом X».

## Конфигурация — плоские переменные окружения (`deploy/env.example`)
`Dirs__*` (папки; свойства `DirectoriesOptions`), `Mail__*` (группы адресатов; `Mail__Default` получает все письма), `Postgres__ConnectionString`, `Oracle__*` (в т.ч. две процедуры), `Smb__*`, `SignatureService__*`, `Smtp__*`, `Courier__PollInterval`. Пути UNC пишутся как есть. На старте сервис проверяет, что всё задано, описание типов корректно (источники, шаги, дубли, маски в общих папках), и создаёт таблицу архива.

## Таблицы PostgreSQL (создаются при старте)
`signed_documents` · `document_state` (только Stateful) · `document_operations` (журнал).

### Архив подписей — `signed_documents`
Таблица `signed_documents` (создаётся при старте): тип, источник, ключ источника, имя файла, код клиента, вид, SHA-256, размер, путь источника, итоговый путь, подпись (bytea), откуда подпись (rest/file), даты. Уникальность: (тип, ключ источника, SHA-256) — запись идемпотентна, первая подпись сохраняется.

## Письма об ошибках — одна сводка за опрос
За опрос копятся все необработанные документы и системные ошибки; в конце опроса уходит **по одному письму на набор получателей** со всеми файлами и причиной по каждому (шаг, причина, ID), сгруппировано по типам. Получатели документа: группа его типа (`NotifyTo`) + `Mail__Default`; `Mail__Default` получает все ошибки, группа — только свои документы, системные ошибки (источник недоступен, некорректная запись) — только `Mail__Default`. Адреса с одинаковым набором получают одно общее письмо. В письме подробно перечисляются до 200 документов, дальше — счётчик «… и ещё N». Пока проблема остаётся, сводка повторяется каждый опрос.

## Ограничения (осознанные)
- Сводка повторяется каждый опрос, пока проблема остаётся (при желании можно добавить ограничение частоты).
- Имена файлов должны быть уникальны среди документов, находящихся в работе в одной папке (документ ищется по имени).
- После перемещения файла отдельно остаётся удаление `.sig`: сбой между ними оставит «осиротевший» `.sig` (на обработку не влияет).
- Если после создания записи в Oracle путь назначения успеют занять (редкая гонка), повтор определит новый путь — процедура Oracle должна переживать повторный вызов.
- Одна реплика; перезапуск пода безопасен.
